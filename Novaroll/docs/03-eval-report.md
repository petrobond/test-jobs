# Отчёт eval (качество, скорость, стоимость)

Прогон: `python scripts/run_eval.py` на 16 синтетических письмах (golden set).
Модель-экстрактор: **`deepseek-flash`** (DeepSeek V4.1-Flash, thinking выключен).
Генератор синтетики: **`deepseek-v4-pro`** (другая модель — «чистота эксперимента»).
Сырые данные: `data/eval_report.json`, `data/eval_items.jsonl`.

## Что здесь реально хорошо
- **Контактные и адресные поля извлекаются идеально** (`company`, `contact_name`, `contact_email`,
  `contact_phone` — 100% и по точности, и по полноте). Это ядро задачи: то, ради чего менеджеры
  и мучаются с ручным переносом.
- **JSON-контракт железный**: 100% карточек проходят схему (в т.ч. благодаря repair-повтору).
- **Ноль ложных тревог**: флаг «проверьте» не дёргается на нормальных карточках — менеджер не тратит
  время зря.
- **Стоимость и скорость**: ~$0.0003 за письмо и ~3 c на p95 — сотни писем в день стоят центы.

## Честно о слабых местах и их причинах
1. **`urgency` (62–75%)** — сравнение двух независимых LLM на субъективной шкале. Примеры:
   - e013: в письме «до конца следующего месяца, крайний срок 15.06» — генератор разметил `high`,
     модель сказала `medium`. **По здравому смыслу модель права** (срок через месяц — не срочно).
   - e002/e004/e016: заявки без срока — генератор разметил `low`, модель `medium`. Оба варианта защитимы.
   Вывод: низкая цифра в основном отражает **расхождение трактовок**, а не ошибку извлечения.
   Направление улучшения: калибровать срочность **детерминированно** от даты дедлайна относительно
   даты получения письма, а «свободную» оценку оставить как фолбэк.
2. **`product` (81%, recall 92%)** — часть расхождений из-за строгой разметки: письмо упоминает «CRM»,
   модель это вернула, а в эталоне `null`; либо синоним («software» vs «IT solutions»).
3. **`requested_deadline` (81%)** — модель пропустила дату в одном письме и вывела дату там, где
   генератор её не заложил (частично шум разметки; даты писала та же LLM).
4. **`needs_review` recall 50%** — метрика оценивает, поймал ли флаг **ошибки**. Но система не может
   «знать», что она ошиблась в субъективной срочности; флаг честно ловит **детектируемые** риски:
   битый ответ, значение без подтверждения в письме, низкую уверенность, пустую суть, отсутствие
   контакта. Расхождения по субъективным полям недетектируемы по построению.

## Как ловили галлюцинации и ошибки
- `evidence`-цитата на каждое значение + проверка, что значение встречается в письме (со стеммингом
  под русские словоформы). Значение без подтверждения → флаг «проверить».
- Валидация Pydantic-схемой (запрет лишних полей, enum для срочности) + один repair-повтор.
- Regex-фолбэк для e-mail/телефона (добор пропущенного моделью).
- Fail-open: сбой вызова LLM → карточка пустая, но флаг «проверить» стоит; письмо не теряем.

## Что проверяли про стоимость/скорость
- Считаем токены из ответа API и цену `deepseek-flash` (off-peak: $0.15/1M вход, $0.60/1M выход).
- Латентность меряем вокруг вызова (p50/p95).

## Ограничения этого замера
- Всего **16 писем** — статистика слабая, доверительные интервалы широкие; цифры по субъективным
  полям «дышат» между прогонами (DeepSeek не полностью детерминирован даже при temperature=0).
- Разметку срочности/продукта делала LLM-генератор — эталон субъективен по этим полям.
- Для серьёзного приёмочного замера нужно 50–100 писем и, лучше, разметка человеком + правило
  калибровки срочности.
