Прогон: `python scripts/run_eval.py` на 16 синтетических письмах (golden set).
- **Модель-экстрактор** (аналитика): **`deepseek-flash`** (DeepSeek V4.1-Flash, thinking выключен).
- **Генератор синтетики**: **`gpt-4o`** (OpenAI) — другой вендор, «чистота эксперимента».

Сырые данные: `data/eval_report.json`, карточки — `data/eval_items.jsonl`.
Пересчёт без вызовов API: `python scripts/run_eval.py --from-items data/eval_items.jsonl`.

## Что здесь реально хорошо
- **Все структурированные поля — 100%**: компания, имя, e-mail, телефон, продукт, срок, язык.
  Это ядро задачи — то, ради чего менеджеры мучаются с ручным переносом.
- **JSON-контракт железный** (100% проходят схему, в т.ч. благодаря repair-повтору).
- **Ноль галлюцинаций и ноль ложных тревог** — на нормальных карточках менеджера не дёргаем.
- **Стоимость и скорость**: ~$0.0003 за письмо и ~3 c на p95.

## Честно о слабых местах и их причинах
1. **`urgency` 75%** — единственное субъективное поле. Причина — разные конвенции у двух LLM:
   - письма без признаков срочности генератор размечает то `low`, то `medium` (в эталоне даже
     однотипные письма размечены по-разному);
   - модель по умолчанию ставит `medium`; правило добирает `high/medium` по явным сигналам
     (замечание: для «до конца недели» правило даёт `medium` даже при слове «срочно», для явной
     даты — `high`). Мы подняли точность правилом с 62% до 75%, но **идеально детерминированно
     эталон не воспроизводится — он сам противоречив**.
   Улучшение: единая рубрика срочности + третий LLM-судья или разметка человеком.
2. **`needs_review` recall 25%** — метрика оценивает, поймал ли флаг ошибки. Но система не может
   «знать», что ошиблась в **субъективной** срочности; флаг честно ловит только **детектируемые**
   риски: битый ответ, значение без подтверждения в письме, низкую уверенность, пустую суть,
   отсутствие контакта. Ошибки в субъективных полях недетектируемы по построению.

## Как ловили галлюцинации и ошибки
- `evidence`-цитата на каждое значение + проверка, что значение есть в письме (со стеммингом под
  русские словоформы). Значение без подтверждения → флаг «проверить».
- Валидация Pydantic-схемой (запрет лишних полей, enum для срочности) + один repair-повтор.
- Regex-фолбэк для e-mail/телефона; правило срочности из слов/сроков.
- Fail-open: сбой вызова LLM → пустая карточка, но флаг «проверить»; письмо не теряем.

## Что проверяли про стоимость/скорость
- Токены берём из ответа API, цену — `deepseek-flash` (off-peak: $0.15/1M вход, $0.60/1M выход).
- Латентность — вокруг вызова (p50/p95).

## Ограничения этого замера
- Всего **16 писем** — статистика слабая, доверительные интервалы широкие; по субъективным полям
  цифры «дышат» между прогонами (DeepSeek не полностью детерминирован и при temperature=0).
- Разметку срочности/продукта делал LLM-генератор — эталон по этим полям субъективен.
- Для приёмочного замера нужно 50–100 писем и, лучше, разметка человеком.

## Эволюция метрик (что показали итерации)
1. Первый прогон: `requested_deadline` recall **0%** — оказалось, **генератор выдумывал даты**,
   которых в письме нет («до конца недели» → конкретная дата). После ужесточения промпта генерации
   (дата только если явно в письме) — **100%**.
2. `product` сначала 81% — часть «промахов» оказалась словоформами («офисная мебель» vs «офисной
   мебели»); добавили сравнение со стеммингом — **100%**.
3. `urgency` в первом эталоне содержала `null` (7 из 16) — считали только размеченные письма и
   усилили правило; 62% → **75%**.
