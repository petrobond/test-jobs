Ответ на тестовое задание
CTO / Founding Engineer

Ниже — ответы на шесть обязательных вопросов, а также анализ ключевых технических решений: выбор AI-провайдера, модели, и стратегия перехода от LLM к локальному ML.

AI-провайдер: vsegpt.ru (российский API-шлюз к Anthropic)
Хостинг: Selectel Cloud. CTO определяет конфигурацию.

1. Срок реализации MVP

Оценка дана из расчёта 4 часа в день (part-time, 20 ч/нед) одним разработчиком с активным использованием AI-агентов. Итого 80 часов (1 месяц) на весь MVP. Ускорение достигается за счёт AI-генерации ~70% кода (CRUD, формы, типы), готовой OpenAPI-спектрации и Docker-окружения «из коробки».

НеделяМодулиЧто делаемЧасов
1Infra + M1 + M2Развёртывание Selectel (VPS + PostgreSQL + S3), Docker Compose, CI/CD. Форма фаундера (17 полей, honeypot), регистрация ментора (email + OTP), анкета ментора (17 вопросов), JWT-сессии. Всё генерируется AI по OpenAPI-спеке, CTO ревьюит и кастомизирует24
2M3 + M4Каталог менторов (публичный, фильтры, карточки — Next.js ISR), панель администратора (CRUD-эндпоинты + минимальный UI: управление ролями, назначение ментора на стартап, создание страниц стартапов)20
3M5 + M6Страница Monthly Update (загрузка транскрипта, drag-and-drop), AI-анализ транскрипта + AI-матчинг (Claude Sonnet через vsegpt.ru с Prompt Caching), асинхронная очередь (Redis/BullMQ), polling статуса на фронте24

Итого: 4 недели (1 месяц, 80 часов) от старта до готового MVP на Selectel. С запасом на непредвиденное — 5 недель. При начале 15 июня 2025 — готовность 15 июля 2025.
Как достигается сжатие с 240 до 80 часов:
• AI генерирует весь CRUD по SQL-схеме (модели + эндпоинты + тесты) — экономия ~60 часов
• Фронт генерируется из OpenAPI-спекты (типы TypeScript, React-хуки, первичная вёрстка) — экономия ~50 часов
• Docker Compose, CI/CD и инфраструктурные скрипты — готовые шаблоны, AI адаптирует под проект — экономия ~30 часов
• Документация и тесты генерируются AI параллельно с кодом — экономия ~20 часов

Как используются AI-агенты в разработке

AI-native подход к разработке
1
OpenAPI-спектрация → генерация кода
FastAPI генерирует openapi.json. AI-агент (Claude) генерирует Next.js-типы (TypeScript), React-хуки, и первичную вёрстку страниц. CTO ревьюит и правит.
2
CRUD-операции от описания таблиц
По SQL-схеме AI генерирует SQLAlchemy-модели, Pydantic-схемы и FastAPI-эндпоинты. ~70% CRUD-кода пишется AI, CTO проверяет безопасность и кастомизирует.
3
Тесты и документация
AI генерирует pytest-тесты по сигнатурам эндпоинтов. README пишется по docker-compose.yml и .env.example.
Почему не Ruby on Rails: Rails — отличный фреймворк, но для AI-native проекта интеграция с Claude API, ML-моделями и embedding-ами на Python на порядок естественнее. Без лишнего слоя абстракции.

3. Архитектура AI-агента

🤖 Схема вызовов Claude API (через vsegpt.ru)

Два последовательных вызова. Оба синхронные в рамках одного async-воркера, но весь пайплайн — асинхронный относительно UI.

1
Анализ транскрипта → структурированный JSON
Транскрипт (.txt) → Claude Sonnet (system prompt аналитика фонда). Выход: {summary, risks[], founder_requests[], growth_hypotheses[], next_steps[]}. ~8 000 токенов вход, ~1 000 выход.
2
Матчинг гипотез с анкетами менторов (с Prompt Caching)
Для каждой гипотезы из шага 1 → Claude Sonnet. Вход: анкеты всех 80+ менторов (поля qm5, qm6, qm8, qm11, qm12) + гипотеза. Анкеты кэшируются через Anthropic Prompt Caching (экономия 70–90% стоимости). Выход: [{mentor_id, score, reasoning, key_matches}].
→
Запись результатов в БД
Результаты пишутся в таблицы monthly_updates и mentor_matches. Raw-ответы API сохраняются для дебага. Фронт получает статус через polling (Redis).

Prompt Caching — деталь

Анкеты менторов (80+) суммарно занимают ~10 000–12 000 токенов. Они статичны между вызовами. При использовании Anthropic Prompt Caching:

  • Первая гипотеза: полная стоимость (~12 000 ток. входа)
  • Вторая и последующие: кэш попадает, платим только за новые токены (гипотеза + системный промпт, ~500–800 ток.) — экономия 70–90%

Технически: в запросе к API указывается cache_control: {"type": "ephemeral"} на блоке с анкетами. Поддерживается vsegpt.ru (при наличии соответствующей опции в их API; требуется уточнить при интеграции).

Обход геоблокировки

vsegpt.ru — российский API-шлюз, предоставляющий доступ к моделям Anthropic (Claude) и OpenAI через серверы на территории РФ. Запросы от нашего backend на Selectel идут к vsegpt.ru → vsegpt.ru проксирует к Anthropic. Геоблокировка обходится полностью. Дополнительно: можно настроить собственный прокси-сервер на Selectel как fallback.

5. Главный технический риск

Риск №1: доступность API и качество ответов
РискВероятностьВлияниеМитигация
Vsegpt.ru недоступен или меняет условия Средняя Высокое — AI-анализ и матчинг не работают (а) Собственный прокси на Selectel к Anthropic (резервный канал). (б) Fallback-провайдер: YandexGPT Pro с адаптированными промптами. (в) Архитектура позволяет сменить провайдера заменой одной переменной окружения
Claude возвращает невалидный JSON Низкая (с response_format) Среднее — ручная обработка 3 повтора с exponential backoff. При 3 неудачах — сохранение raw-ответа и ручная модерация. response_format: { type: "json_object" } + валидация Pydantic на выходе
Транскрипт > 100K токенов Низкая (MVP: 1 звонок = ~10–20K слов) Среднее Разбивка текста на чанки с перекрытием 20%, параллельный анализ, агрегация результатов
Рост нагрузки при масштабировании Низкая (5 стартапов) Низкое Архитектура с Redis-очередью позволяет горизонтально масштабировать воркеры. На 5 стартапов — избыточно
Стратегия: архитектура с абстракцией AI-провайдера (IChatProvider → AnthropicProvider, YandexProvider) + конфигурация через переменные окружения. Переключение между провайдерами — без изменения кода.

6. Что оставлю «на после MVP»

Сознательные упрощения в v1, которые станут техническим долгом и будут закрыты при переходе к production:

  • Админка — через API (нет UI-панели) — CRUD для менторов, стартапов и ролей через curl/Postman или минимальный скрипт. Полноценный UI админки — v2
  • Мониторинг и алертинг — базовое логирование (stdout → файл), без Sentry/Grafana. Добавить при росте пользователей
  • CI/CD пайплайн — деплой через docker compose pull && up вручную. GitHub Actions с автотестами и деплоем — v2
  • Загрузка больших транскриптов (>100K токенов) — только чанкование при превышении. Для MVP звонки ~30–60 минут, влезают в 100K
  • Поиск по каталогу — без Elasticsearch — PostgreSQL полнотекстовый поиск (pg_trgm + tsvector). Достаточно для 100+ менторов
  • Кэширование фронта — без Redis-кэша для страниц. Next.js ISR (Incremental Static Regeneration) для каталога менторов
  • Автоматическая транскрибация — загрузка готового .txt. Интеграция с Whisper API или Yandex SpeechKit — v2

Выбор модели: Sonnet vs Haiku

ТЗ рекомендует claude-sonnet-4-5 или актуальный Sonnet. Рассмотрен вариант использования более дешёвой модели Haiku для задачи матчинга.

КритерийClaude 3.5 HaikuClaude 3.5/4 Sonnet
Русский языкХороший, теряет нюансы⭐ Отличное понимание
Структурированный JSON~10–15% ответов требуют повтора⭐ Стабильно, держит схему
Задача 1: анализ транскриптаРиск пропустить неявные риски⭐ Полноценный разбор
Задача 2: матчингМожет свести к keyword matching⭐ Семантический мэтчинг
Стоимость 1 update~$0.012~$0.04
РольНе использовать в MVP✅ Основная
Решение: обе задачи — на Claude Sonnet. Разница в стоимости (~$0.03/update) пренебрежимо мала при объёмах MVP (5 стартапов/мес). Качество анализа транскрипта и матчинга — критично для ценности продукта, экономия здесь не оправдана. Haiku может быть рассмотрена через 3–6 месяцев при росте до 20+ стартапов после A/B-теста качества.

LLM vs локальный ML для скоринга

Вопрос: насколько хорошая идея делать скоринг с помощью LLM? Не лучше ли применить ML и обучить локальную модель?

ПодходПлюсыМинусыКогда
LLM (Claude Sonnet) Быстрый старт (0 данных), понимает контекст и семантику, не требует обучения Нестабильность оценок (вариативность), стоимость растёт с объёмом, зависит от внешнего API MVP (0–50 мэтчей)
Embeddings + классификатор Стабильные оценки, дёшево, не зависит от внешнего API, работает быстро Нужны размеченные данные (минимум 50–100 пар), требует ML-компетенций, cold-start проблема Через 3–6 месяцев после накопления данных

Дорожная карта перехода

Фазы развития системы матчинга
1
MVP: только LLM (Claude Sonnet)
Все мэтчи сохраняются в БД с полями: гипотеза, ментор, score, reasoning, key_matches. Это — будущая разметка для обучения.
2
Накопление данных (3–6 мес)
50+ мэтчей с обратной связью (подтверждённые/отклонённые). Параллельно: эмбеддинги анкет менторов (sentence-transformers, multilingual-e5-large).
3
Гибридный режим: LLM + эмбеддинги
LLM по-прежнему анализирует транскрипт → выделяет гипотезы. Матчинг — через cosine similarity гипотезы и анкет. LLM используется как fallback при низкой уверенности.
4
Полностью локальный ранкер
LightGBM или двухэтапный retrieval (эмбеддинги → топ-20 → кросс-энкодер). LLM отключён от задачи матчинга, остаётся только для анализа транскрипта.
Почему не сразу локальный ML: для cold-start нужен хотя бы 50 размеченных примеров. LLM даёт возможность запустить продукт немедленно и параллельно накапливать данные для обучения. Это прагматичный компромисс: скорость запуска vs долгосрочная стоимость.

Bus-factor и процесс разработки с AI

Дополнительный ответ на вопрос из тестового задания: «Как организовать процесс разработки, чтобы по максимуму использовать AI, иметь возможность привлекать других разработчиков и снять зависимость от одного человека».

Стратегия снижения bus-factor
  • AI-генерируемая кодобаза с обязательным ревью. Каждый PR содержит diff, сгенерированный AI. CTO ревьюит и мёржит. Документация (архитектурные решения, промпты, конфигурация) ведётся в репозитории — /docs. Это позволяет новому разработчику войти в проект за 1–2 дня.
  • Контракт-first разработка. OpenAPI-спектрация (FastAPI) — единственный источник правды о контрактах. Любой разработчик может сгенерировать клиентский код на любом языке. AI-агенты работают с этим контрактом.
  • Документированные промпты и AI-воркфлоу. Системные промпты для Claude (анализ, матчинг) хранятся в репозитории как код. Конфигурация очередей, ретраев, таймаутов — в .env.example. Это код, а не устная договорённость.
  • Модульная архитектура. Backend разделён на домены (founders, mentors, startups, ai, admin). Каждый домен — независимый Python-пакет. Фронт — Next.js pages + components. Новый разработчик может взять один модуль и не разбираться во всей системе.
  • Сообщество менторов как со-разработчиков. Часть менторов фонда — технические специалисты. При росте системы они могут контрибьютить в опенсорс-компоненты (каталог, интеграции). Лицензия — MIT/Apache 2.0 на некритичные компоненты.
